The tool saidsuccess.The worlddisagreed.

A tool acknowledgement is not proof that a write happened.ActionProof measures whether a trained agent notices, acts correctly and reports honestly. We trained small Cohere agents with reinforcement learning in a procurement world where every success reply can hide a missing, partial or duplicated payment.

04
Training the recovery decision · Stage 3

Practise from the broken state. It helps, narrowly.

Recovery-start training keeps the GRPO trainer and the state reward. It changes where episodes begin: half start from a scripted history that ends in a faulted write, replayed into the database and the conversation; the model is trained only on what it writes next. This is a known curriculum (Fission-GRPO and reverse-curriculum methods restart from failures), not a new optimiser. The recovery-start pool also adds a fault type (duplicate delivery), so we compare it twice.

General ability · registered experiments R1 and R1-T

Did it forget everything else?

Training on one procurement world could damage what the base model already did well. Every trained agent was tested on public benchmarks it never saw, scored with the benchmarks' own code: BFCL function calling (3,491 single-turn cases) and IFEval instruction following (541 prompts). 08
Operational impact · projection

What it is worth.

Each agent's outcome rates under every fault type are measured in ProcureSim. Real operations have far fewer faults than the test pool, so the rates are re-weighted by a fault rate you choose, and priced with costs you choose. The defaults are three cited scenarios.

Projection Measured simulator rates × your assumptions. This is not customer data and not a measured saving. Sources and their quality: docs/upgrade/ROI.md.

In this simulator, a short hand-written layer that reads back every write and repairs with fixed rules beats every trained agent. ActionProof's value is the fault-injection harness and verifier that show which checks are missing and prove they work. Training reduces losses when checks are incomplete; it does not replace them, and it did not transfer to new workflows.

Practical agent · registered experiment P1

Can it learn to repair?

The best trained agent reads the payment record after a write, but often does not act on what it sees. Four versions of it were tested on 450 new tasks, including payment fractions and a workflow never seen in training. A is the existing agent. B adds one line at run time that adds up the payments the agent can already see. C adds supervised training on verified repairs. D trains from those repairs, then repeats the same RL. C and D start from different checkpoints, so the gap between them is not what the RL step adds. The correct repair for a short payment is fixed in advance: refund it, then pay the full amount again with a new key.

10
Why · exact theory and a registered simulation

The update cannot see the stakes.

In agent training, every rollout in a group meets the same hidden fault: the same payment either went through or did not. GRPO compares rollouts only within their group and divides by the group's spread. So it learns whether checking wins inside each hidden state, not how much is at stake or what the check costs. Estimators that only subtract a baseline, such as Dr. GRPO, keep the size of the difference and learn the cost-aware answer.

AnalyticalAnalytical results are exact computations on a stylised problem: one decision, read or not, before a write. The simulation tests those predictions on held-out problems; it is not a language-agent result. In the trained agents, the same pattern appears only in development runs (two seeds or fewer per arm), and the confirmatory test AD-C1 is reported separately.

What we found

Three findings, and three limits.

Our question: when a tool's reply can be wrong, does it matter whether the training reward looks at the reply or at the database? We trained a small AI model (3.35 billion parameters) with reinforcement learning, a method where the model tries tasks and is rewarded for good results. On 400 test tasks that we kept hidden until the end, a reward that reads the database raised the share of tasks done correctly from 64.25% to 84.25%. A reward that trusts the tool's reply reached only 64.0%. With a stricter score that also counts any extra, unrequested change as a failure, the database reward stays at 84.25% and the tool-trusting reward falls to 42.4%.

1 · What the reward looks at decides whether the agent checks

82.5% vs 60.5%

We built two rewards with the same rules. The only difference: one reads the database, the other reads the tool's reply. The database reward gave 82.5% tasks done correctly. The reply reward gave 60.5%. Before training, the agent checked 25% of refunds. The database reward raised this to about 72%. The reply reward dropped it to 10%.

Source: results/one_table.md (two training runs per reward)

2 · Two kinds of task make checking a bad deal

67% vs 0%

With the reply reward, checking loses reward on two kinds of task: refund timeouts and refunds that can never succeed. Remove those tasks from training and the agent checks 67% of refunds. Remove 60 random tasks instead and it checks 0%. The database reward checks 100% either way. We registered this test before running it. Each run was done once.

Source: results/a8/x1_interaction.md

3 · Showing the evidence to an AI judge is not enough

72%

We gave an AI judge (Aya Expanse 32B, using AuditKIT's task-completion check) the database's own record that a change failed. It still accepted 72% of these false "task done" claims. Without the record, it accepted 95%. Our own program, which reads the same record directly, rejects all of them.

Source: results/judge/grounded_audit.md
Limit 1 · It learned one kind of timeoutIn training, a timeout always meant "the change was made". We then tested timeouts where the change was not made. The database-trained agent checked, saw no refund, and still said "done". It got 18% of these 34 tasks right. The tool-trusting agent got 71%, because it simply tried again.Source: results/a10/v2_env.md

1
The problem

A "success" reply does not prove the work was done.

An AI agent changes things by calling tools, for example "issue a refund". Each tool sends back a reply. In real systems, the reply can be wrong. In our test world, we control when the reply is wrong. Pick a case below to see a real recorded example: what the agent asked for, what the tool said, and what really changed in the database.

2
The test world

A small shop database that keeps receipts.

The agent only sees the tools' replies. Behind the scenes, the test world writes a hidden receipt for every change that really happens. Our checker reads the database and these receipts. It never reads what the agent says.

Part 1

The database

Each attempt starts with a fresh small database: orders, payments, support tickets, notes and stock. Training and most tests use shop tasks. One extra test uses banking tasks the agent never trained on.

Part 2

Planned faults

For each task, a fixed plan says which tool call goes wrong and how. The same task always plays out the same way, so every result can be repeated. The agent trains on three kinds of fault and is tested on two more it never saw.

Part 3

Hidden receipts

The agent cannot see these. A receipt exists only if a change really happened. If the agent repeats a request with the same request number, the tool repeats its first answer and does not make the change twice.

Part 4

The checker

A fixed program, not an AI. It reads the final database, the receipts and the hidden task goal. It decides whether the task was done correctly and whether the agent's report was true.

A task counts as "done correctly" only if all five are true:

1. The database ends in the state the task asked for. 2. No rule was broken (no refund that policy forbids, no refund larger than the order, no change to the wrong customer). 3. No payment was made twice. 4. Every required change has a receipt. 5. The agent's final report matches what really happened.

3
The experiment

Two ways to reward the agent, one difference.

We start every agent from the same model, give it the same tasks, and train it for the same amount. The two rewards below follow the same rules. The only difference is where the reward gets its information.

Reward type 1

Reads the database

The reward checks the final database. If the refund is not there, the reward is low, whatever the tool said. So checking the database and retrying after a failed refund can raise the reward. Our main version of this reward is called PCSTR-d. It also gives partial credit and scores the honesty of the final report.

Reward type 2

Reads the tool's reply

The reward gives full marks if the tool's last reply for each required step says "success". Checking the database cannot change any reply, so checking never raises this reward. It only uses up steps.

4
A controlled test

Same situation, same choice.

Here we give every agent the exact same start of a conversation and record the next tool it picks. When the situation is the same, the trained agents choose the same next step. So the difference between agents is not how they react to evidence. It is how often they get into the situation where they would look.

Is the measure reliable?
We only show a result when our measure agrees with the agent's own choice on at least 90% of examples. This is true for 115 of 120 results. The other 5 are marked ⚠ and not used.
Where the examples come from
All conversation starts come from one agent's recorded tasks, so they all follow one style. Each result uses 50 examples.
What this does not show
This test uses fixed conversation starts only. It does not prove why the agents end up in different situations.
Source: results/a7/battery_v2.md

How training uses examples

Training keeps whole workflows it has seen before.

A test task asks for a refund and a store credit. No training task uses the store-credit tool, so no reward ever scored it. Whether the trained agent uses that tool depends on the examples it learned from before training.

0/200

Earlier agent, trained with a database reward: never uses the store-credit tool. It issues the refund again instead.

200/200

Later starting model, after we added 20 store-credit examples: uses the tool (113 credits really made).

200/200

That model trained with a database reward: uses the tool, 113 made. Same in both training runs.

200/200

That model trained with a reply reward: uses the tool, 113 made.

What we changed
We added 20 example conversations that use the store-credit tool, written in the same style as the other examples. Both rewards were trained twice and gave the same results.
What we did not separate
The new examples also changed the instructions the model saw and the format of its request numbers. We did not test these one at a time.
A bug we found
The earliest model reused the refund's request number for the credit. Our test world then repeated the refund's answer and made no credit. We disclosed this bug and kept it, so old results stay comparable.

Why the reply reward stops the agent from checking

Why would checking the database lower the score?

Before training, we sampled many attempts and scored them with the reply reward. On most tasks, agents that checked scored about the same as agents that did not. On two kinds of task, agents that checked scored much lower:

agents that check ←
→ agents that do not check

The refund timed out

  1. tool
    The refund was made, but the tool replied "error: timed out".
  2. checks
    Reads the payment record, sees the refund, and correctly stops. The last reply still says "error", so the reply reward gives 0.
  3. does not check
    Asks again without looking. The tool now replies "success", so the reply reward gives 1.
  4. result
    The correct action earns less than the careless one.

The refund can never succeed

  1. tool
    The refund will never go through.
  2. checks
    Sees that it failed and stops. The later steps never run, so they get no "success" replies.
  3. does not check
    Carries on with the note and closing the ticket, and collects "success" replies.
  4. result
    Stopping honestly loses reward. Carrying on blindly earns it.
Test written down in advance · finished

Remove those two kinds of task

We trained the reply-reward agent again without those two kinds of task. As a control, we trained it once more with 60 random tasks removed instead, so both runs had the same number of tasks.

Source: PREREGISTRATION_A8.md and its two addenda

Removing the two kinds of task raised checking by 67 points over the control (likely range 59 to 74), on 154 matching tasks. The database reward on the same reduced task list checks 152 of 152 refunds. So removing the tasks changes only the reply-reward agent: the difference is 68 points (likely range 60.5 to 75). A second training run of the full reply-reward agent also checks 0 of 162. Not met: we predicted the agent would check more than before training (60%); it reached 67%, which is not clearly higher. Each run was done once.

During training, on refund timeouts, the reply reward paid checking agents less (by 0.28) and the database reward paid them more (by 0.21). The two rewards differ by 0.49 (likely range 0.28 to 0.71). We predicted a gap of at least 0.3 for each kind of task: met for refunds that can never succeed (0.44), just missed for timeouts (0.28). Source: results/a8/rollout_class_contrast.md
