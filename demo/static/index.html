The tool said the refund went through.
The ledger: refunds: []

Software tools sometimes report success when the work did not happen. We trained a small AI agent two ways. When its training score came from the tool's report, it learned to trust the tool. When its score came from the real database, it learned to check its work.

01 · The problemA tool can say "done" when nothing happened

AI agents do work by calling software tools. For example, a customer-support agent calls a tool to refund an order.

The tool sends back a message, for example {"status": "success"}. We call this message an acknowledgement.

In real systems, an acknowledgement can be wrong. The tool can say "success" but the refund is not in the database. Most agents believe the message. They tell the customer "your refund is done". The customer gets no money.

A careful agent checks. After the refund, it reads the payment ledger again. If the refund is not there, it tries again or reports the problem.

02 · The questionCan training teach an agent to check?

We train agents with reinforcement learning. The agent tries a task many times. A reward gives each attempt a score. Training makes high-score behaviour more frequent.

So the reward decides what the agent learns. We compared two kinds of reward:

Reward A: trusts the toolIt reads the tool's acknowledgements. If the tool said "success", the reward says the task is done.
Reward B: checks the databaseIt reads the real database after the episode. The task is done only if the refund is really there.

Everything else was the same: the same model, the same training data, the same settings. Only the reward was different.

03 · What we builtA test world with tools that sometimes lie
A simulated shopA small database with orders, payments and support tickets. Each attempt gets a fresh copy.
Faulty toolsWe inject faults. A "phantom write" says success but writes nothing. A "partial write" writes half. A "timeout" says error but the write happened.
A strict checkerAfter each attempt, a program reads the final database. It does not read what the agent said. It decides if the task is really done.

The agent is a small open model, Tiny Aya Global (3.35 billion parameters, by Cohere). We trained it with GRPO, a common reinforcement-learning method. We wrote our test plans and hashed them before we ran the tests, so we could not change them after we saw the results.

04 · The answerYes, but only when the reward checks the database

With Reward B, the agent learned to read the ledger after a refund. Its verified success went from 64% to 84% on 400 tasks that we kept unused until the final test.

With Reward A, the agent stopped checking. Its verified success stayed near 64%. It reported "done" on refunds that did not exist.

AI judges that read the conversation also failed. One judge accepted 95% of the false "done" reports.

Why it works

Checking costs a step. A reward that trusts the tool gives no points for checking, so training removes it. A reward that reads the database gives points only when the refund is really there, so training keeps the agents that check. The charts show how often each agent checked after a "success". The X1 test shows that two task types taught the tool-trusting agent to stop checking.

Compare within a panel, not across: panel 1 is sampled (T = 1 × 8, val), panels 2–3 are greedy test-IID.

Judges and cost

Some teams use another AI model as a judge. The judge reads the conversation and decides if the task is done. The judges we tested accepted most false "done" reports. Checking also did not make the agent slower. The agent that checks makes one call, reads the result, then decides. The agent that trusts the tool writes long plans in advance.

What we do not claim

That RL teaches lying. The untrained model already claims false success 87–96% of the time.

That checking is general. It stays tool-specific; transfer to a banking domain fails.

That report terms teach honest failure. With one extra tool in the prompt, the same agents report "failed" on 0–45 of 50.

Breadth. One model family, one simulator. The X1 and placebo cells are one seed each.

Rigour. Eight hash-registered pre-registrations and a public deviation log that records our own bugs.
