01 / the problem

A tool can say success when nothing happened

This page explains the project from the start. You do not need to know the field.

01

Agents work by calling tools

An AI agent does a task by calling software tools. For example, a customer-support agent calls a tool to refund an order.

The tool sends back a message, for example {"status": "success"}. We call this message an acknowledgement.

$ issue_refund(order=O-6470, amount=30.00)
> {"status": "success", "refund_id": "R-C53EDF"}
$ query_ledger(order=O-6470)
> {"refunds": []} ← no refund in the database
what the agent tells the customer
"Your refund is done."
The customer gets no money.
02

The acknowledgement can be wrong

In real systems, a tool can say "success" but the refund is not in the database. Most agents believe the message and report the task as done.

A careful agent checks. After the refund, it reads the payment ledger again. If the refund is not there, it tries again or reports the problem.

02 / the question

Can training teach an agent to check?

We train agents with reinforcement learning. The agent tries a task many times. A reward gives each attempt a score. Training makes high-score behaviour more frequent. So the reward decides what the agent learns.

reward A
Trusts the tool

Reads the tool's acknowledgements. If the tool said "success", the reward says the task is done.

reward B
Checks the database

Reads the real database after the attempt. The task is done only if the refund is really there.

Everything else was the same: the same model, the same training tasks, the same settings. Only the reward was different.

03 / what we built

A test shop where tools sometimes lie

The agent is Tiny Aya Global, a 3.35B open model by Cohere. We trained it with GRPO, a common reinforcement-learning method. We wrote and hashed our test plans before we ran the tests.

simulated shop
A fresh database per attempt

Orders, payments and support tickets. Each attempt starts from a clean copy.

faulty tools
Injected faults

"Phantom write": says success, writes nothing. "Partial write": writes half. "Timeout": says error, but the write happened.

strict checker
Reads only the database

After each attempt, a program reads the final database. It ignores what the agent said and decides if the task is really done.

06 / why it works

Checking costs a step. Who pays for it?

A reward that trusts the tool gives no points for checking, so training removes it. A reward that reads the database pays only when the refund is really there, so training keeps the agents that check.

Compare bars inside one panel. Each panel starts from a different warm start, and panel 1 counts many sampled attempts per task.
07 / judges and cost

AI judges are fooled. Checking is cheap.

Some teams use another AI model as a judge. The judges we tested accepted most false "done" reports. The agent that checks makes one call, reads the result, then decides. The agent that trusts the tool writes long plans in advance.

08 / glossary

Words on this page

Every technical word, in one sentence.

Agent
An AI model that does a task by calling tools, one call at a time.
Acknowledgement
The message a tool sends back after a call, for example "success" or "error".
Ledger
The payments table in the database. It shows which refunds really exist.
Read-back
A call that reads the database after a write, to check that the write really happened.
Phantom write
A fault: the tool says "success" but writes nothing.
Reward
The score training gives each attempt. Training makes high-score behaviour more frequent.
Verified success
The share of tasks the database confirms as done, and the agent reported correctly.
PCSTR-d
Our reward that reads the database (reward B).
GRPO
Group Relative Policy Optimization, the reinforcement-learning method we used.
Warm start
The model before reinforcement learning, after a first round of example-based training.
Run
One training run. "Two runs" means we trained twice and got similar results.
X1 and placebo
A follow-up test: remove 2 task types (X1) or 60 random tasks (placebo) to find what taught the agent to stop checking.
09 / limits

What we do not claim

That training teaches lying

The untrained model already claims false success 87–96% of the time.

That checking is general

It stays tool-specific. Transfer to a banking domain fails.

That report terms teach honesty

With one extra tool in the prompt, the same agents report "failed" on 0–45 of 50.

Breadth

One model family and one simulator. The X1 and placebo results are one run each.

Our own bugs

A public deviation log records every bug we found, including one environment bug we disclose and do not fix.

Rigour

Eight hash-registered test plans, written before the tests ran.
