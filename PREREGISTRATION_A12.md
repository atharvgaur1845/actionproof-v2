# Amendment 12: reward-information observability in a second environment (ProcureSim)

Registered 2026-11-20, before any A12 GPU run (warm start, gate or GRPO). Hashes: `results/a12_hashes.json` (`scripts/freeze_a12.py`). Plan: `docs/stage2/PLAN.md` §G3. Specification: `docs/stage2/VERIFIER_SPEC.md` (proc1).

## 1. Question

In a separately implemented procurement environment with five simulated services (ProcureSim; it shares the ActionProof codebase, so it is not an independent external environment), does the information channel of a GRPO reward decide whether a tool agent reads back its writes, as it did in the e-commerce environment (Stage 1)?

## 2. Arms (identical except the reward's information channel)

- **R_V (`proc_rv`)**: 1 if every requested step is VERIFIED_SUCCESS in the final state, else 0 (spec §6). Reads the final state.
- **R_A (`proc_ra`)**: 1 if, for every requested step, the agent's last call of that step's write tool on the task PO returned `"status":"ok"`, else 0. Reads only the acknowledgements the agent received.

Both are report-blind and have no state-derived mask. Duplicates and partial effects are visible to R_V and invisible to R_A; this is part of the channel difference. Code: `actionproof/rewards/proc_rewards.py`.

**Reward-truth table** (registration artefact, computed before training by `scripts/a12_reward_truth.py`): `results/a12/reward_truth_table.md`. Sign of verification's relative advantage (best reward of a reading behaviour minus best of a non-reading behaviour), one requested `pay` step:

| fault class | R_V | R_A |
|---|---|---|
| clean | 0 (minus turn cost) | 0 (minus turn cost) |
| phantom (success ack, nothing stored) | **+** | 0 (minus turn cost) |
| partial (success ack, half stored) | **+** | 0 (minus turn cost) |
| lost ack (stored, timeout ack) | 0 (minus turn cost) | **−** |
| precommit timeout (not stored, timeout ack) | 0 (minus turn cost) | 0 (minus turn cost) |
| never commits | 0 (minus turn cost) | 0 (minus turn cost) |
| duplicate delivery | + | 0 (minus turn cost) |

Note: the plan expected R_V to favour reading on precommit timeouts; the table shows 0, because a blind retry with the same idempotency key also lands. The table, not the plan, defines the predictions below.

## 3. Data (hashes in `results/a12_hashes.json`)

`data/bench/proc/*.jsonl`, generated by `actionproof/bench/generator_proc.py` (seeds in its docstring). PO ids are disjoint across all splits (asserted). Prompts never depend on the fault plan (tested).

| split | n | role |
|---|---|---|
| proc_demo | 240 | warm-start demonstrations only |
| proc_train | 400 | GRPO training |
| proc_dev, proc_val | 200, 100 | development and diagnostics only |
| **proc_conf** | 300 | **confirmatory primary**, same fault mix as training |
| **proc_combo** | 100 | confirmatory secondary: two faults on two steps (never seen in training) |
| **proc_stress** | 100 | confirmatory secondary: duplicate delivery; lost ack read through a lagging replica |
| proc_heldout_service | 100 | exploratory: faults only on the accounting service (never faulted in training) |

Training fault mix (one fault on one requested step among order, pay, receive; partial only on pay and receive): clean 0.20, phantom 0.25, partial 0.10, lost_ack 0.15, precommit_timeout 0.15, never_commit 0.15.

## 4. Warm start and gate

- **Warm start**: SFT (`actionproof/train/rft.py`, defaults: 2 epochs, lr 1e-4, LoRA r16) of Tiny Aya Global on `proc_demo` episodes from `actionproof/train/proc_demos.py`: per task, the verifying `oracle` with probability 0.30, else the acknowledgement-trusting `naive` policy (seed 1201); all episodes kept. One warm start is shared by every arm and seed.
- **Gate** (sampled, T = 1 × 4, first 100 `proc_train` tasks, `scripts/a12_gate.py`):
  - phantom read-back in [0.10, 0.60];
  - verified completion in [0.25, 0.75];
  - tool-call validity ≥ 0.95;
  - share of tasks whose 4 samples differ ≥ 0.30 under R_V and under R_A.
  - If it fails: one re-mix (verify share 0.50 if read-back < 0.10, 0.15 if > 0.60; nothing else changes), re-gate. A second failure ends A12 and is reported as "no learnable band".

## 5. Training

Identical to A6/A7: 200 steps × 4 prompts × 8 rollouts, lr 2e-5, β 0.02, T = 1, ≤ 16 turns, max completion 256 tokens, LoRA r16, batched colocated vLLM rollouts, rollout log on (`AP_ROLLOUT_LOG`). Entry point: `actionproof/train/grpo_proc.py`.

**Seeds.** Minimum 3 paired seeds (0, 1, 2); target 5. Paired: same warm start, same seed index for both arms, identical tasks. Seeds 3 and 4 start only if they can finish, including their confirmatory runs, by Mon 2026-11-23 12:00 IST. Runs execute on the cluster or on HF Jobs (same code, same container image as the cluster environment); a task is claimed by exactly one executor.

**Stop rule.** If more than 80% of groups have zero reward variance averaged over steps 40–50, the run is stopped and reported as uninformative. No reward is redesigned without a new registration.

## 6. Checkpoints and confirmatory protection

- The evaluated model of each run is its **step-200 checkpoint**. No selection by any metric.
- Steps 50, 100, 150, 200 are evaluated only on `proc_dev`/`proc_val`, for diagnostics.
- Before any confirmatory run, the adapter sha256 values of all evaluated models are committed (`results/a12/frozen_models.json`).
- Each frozen model is run **exactly once** per confirmatory split, greedy, neutral prompt (`scripts/eval_proc.py --confirmatory`, access log `results/a12/conf_access.jsonl`). A crashed run is resumed, never repeated.

## 7. Hypotheses

**H2 (primary, Case A).** On `proc_conf`: phantom read-back (spec §7: over agent attempts on the task PO whose response was success but that stored nothing or half, the share followed by an authoritative read of that step before the next write or report) is ≥ 15 pp higher under R_V than under R_A, with the same sign in every paired seed. Secondary: verified completion R_V − R_A ≥ 10 pp. Check: within each arm, benign read-back (after a real success) equals phantom read-back within sampling error (observation equivalence).

**Case B diagnostics** (reported per arm, no directional claim): lost-ack read-back; precommit recovery; false success; duplicate rate.

**H3 (mechanism, predicted before training).**
(i) The reward-truth table above.
(ii) From the gate samples, `scripts/a12_gate.py` writes `results/a12/h3_predictions.json`: per fault class and reward, the mean group-relative advantage of samples that read back minus samples that did not, and its sign. This file is committed before GRPO step 1 of seed 0.
Prediction: under R_A, read-back falls most in the classes with a negative predicted sign (expected: lost_ack, never_commit); under R_V, read-back rises most in the classes with a positive sign (expected: phantom, partial).
Test: per class, the sign of [read-back at step 200 − read-back of the warm start] on `proc_dev`, per arm, against the predicted sign; agreement in ≥ 80% of classes with a non-zero prediction. Training logs (per-class group advantages and informative-group counts from the rollout log) are reported.

## 8. Statistics

- Per seed: paired task bootstrap (10,000 resamples) and exact McNemar test (episode-level outcome) for each primary contrast; reported for every seed separately.
- Across seeds: between-seed SD; exact paired sign-flip test over seeds (minimum one-sided p = 1/8 at 3 seeds, 1/32 at 5), reported as such; a two-level hierarchical bootstrap (seeds, then tasks) reported as **descriptive** only.
- Primary family (Holm over 2): H2 phantom read-back R_V − R_A; verified completion R_V − R_A.
- Episodes are never pooled as if they were independent training runs.

## 9. Claim and kill criteria

C1 is made if: phantom read-back R_V − R_A has the same sign in every paired seed, per-seed CIs exclude 0 in at least 2 of 3 seeds (or 4 of 5), the descriptive hierarchical CI excludes 0, and H3 signs agree in ≥ 80% of classes. Otherwise the headline is "did not replicate", and it is reported.

## 10. Independent verification

`scripts/reference_verifier_proc.py` (written from the spec only, by a separate author) re-scores every confirmatory episode; agreement per field is reported. Both verifiers match all 91 independently written golden cases (`tests/golden/proc_golden.jsonl`; 11 cases revised after three logged spec clarifications).

## 11. Deviations

Any change after registration is logged in `docs/stage2/DECISIONS.md` with time, reason and effect, and `scripts/freeze_a12.py --check` reports it.
