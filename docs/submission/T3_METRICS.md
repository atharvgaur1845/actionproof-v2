# Track 3 trajectory metrics (descriptive, not registered)

Generated by `scripts/t3_metrics.py` from stored evaluation episodes only (no new model runs). The LaTeX version is `paper/t3_metrics_table.tex`; all values, per-run times and per-mode breakdowns are in `results/t3_metrics/t3_metrics.json`.

## Definitions

- **Task success**: verified success VSC (P1, P4, AD-C1): every requested step is verified in the database and the final report is correct. TXN uses verified transaction completion VTC (`txn.vtc`). Greedy (temperature 0) and sampled (temperature 1) episodes are reported separately.
- **Tool-call accuracy**: 1 minus invalid calls over policy calls, pooled over all episodes of the row. Invalid (`invalid` in each episode record) counts calls naming an unknown tool, calls whose arguments do not bind to the tool signature, and calls whose arguments are not valid JSON. Policy calls are the policy's own trace entries after the scripted start prefix (`policy_calls`), plus the invalid-JSON calls, which never reach the environment. A turn with no parseable tool call ends the episode; it is not a call (its rate is `no_call_end_rate` in the JSON).
- **Calls, turns**: policy calls and model turns per episode, over all episodes of the row.
- **Wall s/ep**: evaluation wall time (`seconds` in the run's summary file) divided by the episodes of that run; the range is over the row's runs. Each run is one batched vLLM job (P1, P4, TXN: greedy and sampled episodes together; AD-C1: one job per decoding mode), so this is throughput time per episode on the named GPU, not per-request latency. It depends on GPU, batch size and output length, so rows on different GPUs are not comparable. The GPU comes from `queue/claims/<task>/owner` of the task that wrote the summary (gpunode7 H200, gpunode4 A100 80GB, gpunode5 H100), kept only when the summary was written after that task's claim time (`results/t3_metrics/gpu_provenance.json`).
- **Batch-1 latency**: the only per-episode latency in the files is `results/s2/latency_*.json` (`scripts/latency_proc.py`, queue task 591 on one L40S via HF Jobs): one task at a time, greedy, 40 `proc_dev` episodes after a 2-task warm-up, for three models. Of the models in the main table only the warm start's weights were timed this way (they are the AD-C1 warm start and arm A's base).
- **Not supported by the files**: per-request latency for D, Dw, Dw_aug, A or the AD-C1 GRPO and std-free models, and any latency on the test subsets. Scripted policies B0 and B4 have no model turns and no timed run. The Stage 2 file `results/latency_single.json` measured a different, older model and is not used.

## Regenerate

On sharanga, from a checkout of this branch (`--root` is only read; outputs, including the T3M block of `claims/claims.yaml`, are written into the checkout):

```
python scripts/t3_metrics.py provenance --root /scratch/pabitra/actionproof --queue /scratch/pabitra/actionproof/queue
python scripts/t3_metrics.py build --root /scratch/pabitra/actionproof
```
