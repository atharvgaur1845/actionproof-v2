# ActionProof: what the reward can see decides whether a tool agent checks its writes

**Track 3 · AgentTune → AuditKIT · Tiny Aya Global 3.35B**

When tool acknowledgements can contradict execution state, does the information source of a reinforcement-learning reward change whether an agent checks its own writes? In ActionProof, a SQLite support environment, failed writes can return a byte-identical success acknowledgement, and a deterministic verifier scores each episode from database state. On 400 untouched, pre-registered confirmatory tasks, GRPO with a state-grounded reward (PCSTR-d, two training seeds) raises verified-success completion (VSC) from 0.6425 for the warm start to 0.8425; a tool-trusting reward reaches 0.640 (difference +20.25 pp [16.4, 24.3]). On strict VSC, which also forbids unrequested writes, PCSTR-d stays at 0.8425 and the tool-trusting reward falls to 0.424.

The reward's information source decides evidence acquisition. With two rewards of identical form from one warm start, differing only in the goal term's source, test-IID VSC is 0.825 against 0.605, and sampled refund read-back rises from 0.25 to 0.71–0.72 under the database reward but falls to 0.10 under the acknowledgement reward. Task composition can make checking actively costly: on refund timeouts and unrecoverable refunds, acting on a read forfeits success acknowledgements. In a pre-registered intervention, removing those two task classes restores read-back to 0.669, removing 60 random tasks leaves it at 0.000, and the state reward reads back 1.000 on both pools (interaction +0.678 [0.605, 0.750]; the interval is over tasks, with one training seed per cell). An LLM judge given the database's receipt ledger still accepts 72% of the false completions it exposes.

The acquired behaviour is fragile. In a stress test where a timeout can fail before the commit, the state-trained agents read the order and still report success, scoring 0.18 VSC against 0.71 for the tool-trusting agent on 34 tasks. This is consistent with GRPO amplifying behaviours already present after supervised fine-tuning rather than acquiring a general verification capability. An independently implemented verifier, sharing no verification code, replays every confirmatory episode from its initial database and reproduces our VSC on all 4,000 (400 tasks × 10 runs: the warm start and nine GRPO runs).
